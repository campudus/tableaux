# vertx-pg-client is strict about bind types; three concrete workarounds in SQLConnection.scala

Unlike the old JDBC-style `vertx-mysql-postgresql-client`, the reactive `vertx-pg-client` requires the Java type of every bound parameter to exactly match what Postgres reports for that position, and its `Transaction` API has a documented, unfixed command-ordering bug. Three non-obvious things had to change to keep the 189 existing call sites working unmodified (see ADR 0003):

1. **Type coercion in `SQLConnection.toBindValue`.** Call sites bind uuid/timestamptz/date/text[] values as plain Strings/JsonArrays (e.g. `someUuid.toString`, `langtags.mkString("{",",","}")`), relying on Postgres to cast them — the old client tolerated this, pg-client does not (`can not be coerced to the expected class`). `toBindValue` detects these shapes by regex/pattern and converts them back to `java.util.UUID`, `java.time.OffsetDateTime`/`LocalDate`, or `Array[String]` before binding.

2. **jsonb/json double-encoding.** pg-client's jsonb encoder calls `Json.encode(value)` on whatever Java object it's given. Call sites that pre-serialize JSON to a `String` before binding (e.g. `someJsonObject.encode()`) end up with the JSON text encoded *again* as an escaped JSON string scalar — invisible on a simple write-then-read-back round trip, but breaks any SQL-side JSON op (`existing_jsonb || ?::jsonb` degrades into scalar-wrapping instead of array concatenation). Fixed two ways: `toBindValue` parses JSON-shaped strings back into `JsonObject`/`JsonArray` before binding, but only when the SQL text contains an explicit `::jsonb`/`::json` cast (`HasJsonCast` regex) — otherwise a genuine `text` column that happens to contain JSON-looking content (e.g. `system_settings.value`) would be wrongly parsed. Every INSERT/UPDATE that binds pre-stringified JSON against a `jsonb`/`json` column therefore needs an explicit `::jsonb`/`::json` cast in its SQL text, even where Postgres could otherwise infer the type from the column - grep for `.encode()` / `.getJson.toString` near `Json.arr(` before adding a new one.

3. **`Transaction` API command ordering.** pg-client's `conn.begin()`/`tx.commit()`/`tx.query()` can send commands out of order against the wire-level transaction (see [eclipse-vertx/vertx-sql-client#312](https://github.com/eclipse-vertx/vertx-sql-client/issues/312), closed wontfix), surfacing as a spurious `current transaction is aborted` on a later, unrelated statement. `SQLConnection.transaction()` avoids the `Transaction` object entirely and drives the transaction with plain `BEGIN`/`COMMIT`/`ROLLBACK` text against a checked-out `SqlConnection`.

One related model-code change fell out of investigating (3): `RowModel.updateLinks` used to insert multiple links in one UNION-ed multi-row `INSERT ... RETURNING *` statement with 9 bind parameters per link. Past roughly two links (18 parameters), pg-client's prepared-query path reliably failed the *entire* statement with the same `current transaction is aborted` error - not reproducible via plain `psql`/`PREPARE`+`EXECUTE` with the identical SQL and parameters, so the cause looks pg-client-internal rather than a real SQL problem. Rewritten as one single-row `INSERT` per link, executed sequentially in the same transaction; the per-row cardinality check's offset changed from `index + 1` to a flat `+ 1` since each insert now sees the real, already-updated row count from the previous one instead of a shared pre-insert snapshot.
